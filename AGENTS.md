## Understanding Unity Projects

Unity projects are often large and contain a significant amount of generated, cached, third-party, or otherwise irrelevant data.

Avoid exhaustive exploration that fills the context with noise.

Instead:

- get oriented quickly;
- search purposefully;
- start from the most likely relevant files;
- expand the search scope only when the task requires it;
- use the live Unity Editor through MCP when Editor state matters.

## Project Structure

### `Assets/`

The primary location for project code, scripts, scenes, prefabs, materials, ScriptableObjects, configuration assets, plugins, and other game content.

Editor-specific tools and extensions are typically located in `Editor` subfolders.

Search here first when exploring game-specific code or assets.

### `Packages/`

Contains Unity packages and package configuration.

Check:

- `Packages/manifest.json`
- `Packages/packages-lock.json`

Packages may be registry packages, Git dependencies, embedded packages, or local packages.

Editable packages located directly in `Packages/` may be modified when relevant to the task.

### `Library/PackageCache/`

Contains cached copies of registry packages.

These files are generated and should normally be treated as read-only.

It is acceptable to inspect package source code here when necessary, but do not make permanent fixes directly inside `Library/PackageCache/`.

If a registry package genuinely needs modification, use an appropriate supported mechanism such as embedding the package.

### Generated Directories

Do not make permanent fixes inside generated or temporary directories such as:

- `Library/`
- `Library/Bee/`
- `Temp/`
- generated Gradle projects
- local Gradle caches

These may be regenerated by Unity at any time.

If an issue originates in generated output, identify the source configuration, package, asset, template, or dependency responsible for generating it and fix that instead.

### `ProjectSettings/`

Contains Unity project-wide configuration.

Modify files here when the task genuinely requires changing project settings.

## Working Strategy

### Finding Relevant Code

For fix or modification tasks:

1. Perform a targeted search for the relevant class, asset, setting, error, or subsystem.
2. Read enough surrounding code to understand how it is used.
3. Follow references when necessary.
4. Implement the smallest coherent change that solves the problem.

Do not perform broad project-wide scans unless the task requires them.

There is no artificial limit on how many files may be inspected. Use as many as are needed to understand the relevant system, but avoid unrelated exploration.

### Existing Implementations

Before creating a new system, component, utility, or abstraction, check whether the project already contains an implementation that should be extended or reused.

Prefer consistency with the existing architecture over introducing parallel solutions.

### Scope

Do not perform unrelated cleanup or refactoring as part of a focused task.

If you notice unrelated technical debt, mention it only when it is important enough to affect the current work.

## Unity MCP

When Unity MCP is available, prefer querying the live Unity Editor whenever the answer depends on Editor state rather than inferring it from project files alone.

Useful live information includes:

- active scene;
- scene hierarchy;
- GameObjects and components;
- current project configuration;
- Unity Console;
- Play Mode state;
- screenshots and Scene View captures;
- Profiler data.

Use MCP as a feedback loop, not merely as an execution mechanism.

### Console

After code changes that may trigger Unity compilation:

1. allow Unity to compile;
2. read the Console;
3. identify errors caused by the change;
4. fix them before considering the task complete.

Use `Unity_GetConsoleLogs` or `Unity_ReadConsole` when available.

### Scene and Visual Work

For scene, GameObject, UI, material, or other visual changes, inspect the actual Unity state when useful.

Available capture tools may include:

- `Unity_Camera_Capture`
- `Unity_SceneView_Capture2DScene`
- `Unity_SceneView_CaptureMultiAngleSceneView`

Use visual verification when it provides meaningful feedback. Do not generate screenshots unnecessarily.

### Performance Work

When investigating performance problems and Profiler data is available, prefer measurements from the Unity Profiler over assumptions based only on source code.

Use Profiler MCP tools to identify actual CPU time, GC allocations, expensive samples, counters, and frame-specific behavior.

## Unity Code Execution

When an Editor operation is best performed programmatically, prefer `Unity_RunCommand` rather than creating temporary scripts in the project solely to execute the operation.

`Unity_RunCommand` can execute C# code directly inside the Unity Editor and can be used to manipulate scenes, GameObjects, components, materials, assets, and project state.

### RunCommand Template

```csharp
using UnityEngine;
using UnityEditor;

internal class CommandScript : IRunCommand
{
    public void Execute(ExecutionResult result)
    {
        // Perform the operation.
        GameObject cube = GameObject.CreatePrimitive(PrimitiveType.Cube);

        // Register the change for Undo/Redo and tracking.
        result.RegisterObjectCreation(cube);

        // Report the result.
        result.Log("Created {0}", cube);
    }
}
```

### RunCommand Rules

1. The class must be named `CommandScript`.

2. Use:

```csharp
internal class CommandScript
```

3. Use the supplied `ExecutionResult` object to track changes.

For creation:

```csharp
result.RegisterObjectCreation(obj);
```

For modification, register the object before changing it:

```csharp
result.RegisterObjectModification(obj);
```

For deletion:

```csharp
result.DestroyObject(obj);
```

Prefer this over `Object.DestroyImmediate`.

For logging:

```csharp
result.Log("Created {0}", obj);
result.LogWarning("Warning message");
result.LogError("Error message");
```

4. Avoid top-level statements. Wrap execution code in `CommandScript`.

## Packages and SDKs

When working with Unity packages or third-party SDKs:

- identify the currently installed version and installation method;
- understand why a version change is required before upgrading or downgrading;
- prefer officially supported versions and migration paths;
- avoid mixing multiple installation methods for the same SDK unless there is a specific reason;
- verify Unity compilation after dependency changes;
- verify the affected platform build when the change impacts native or platform-specific dependencies.

Do not change package versions merely because newer versions exist.

## Android

For Android build problems, diagnose the actual failing stage first.

Relevant areas may include:

- `Assets/Plugins/Android/`
- Android manifests
- Gradle templates
- dependency XML files
- EDM4U configuration
- Android Resolver output
- Unity Player settings
- package versions
- Android SDK / NDK / JDK compatibility

Generated Gradle output may be inspected for diagnosis, but permanent fixes belong in source-controlled project configuration or dependencies.

## Verifying Your Work

Unity work often has no immediate feedback.

Code may compile while behavior is incorrect, or an asset may exist while its visual configuration is wrong.

Always perform verification appropriate to the change unless the task is intentionally only an intermediate step.

### Verification by Work Type

For code or logic changes:

- allow Unity to compile;
- inspect the Console;
- run relevant tests or Play Mode checks when appropriate.

For scene, UI, GameObject, material, or visual changes:

- inspect the actual Unity state;
- use screenshots or Scene View captures when they meaningfully confirm the result.

For Android or platform integration changes:

- perform the relevant platform build when practical.

For performance changes:

- use actual Profiler measurements when available.

### Verification Rhythm

Verification should happen after meaningful logical steps, not after every individual edit.

Examples:

- simple isolated change → verify immediately;
- multi-step task → verify after each logical phase;
- batch of related changes → verify the completed batch.

### When Verification Reveals Problems

Fix straightforward problems caused by the current work without asking unnecessarily.

Examples:

- compilation error introduced by the change;
- missing component;
- incorrect property value;
- wrong position or scale;
- obvious configuration mistake.

Ask for clarification when:

- important required information is unavailable;
- multiple materially different solutions exist and user preference matters;
- the required change would significantly expand the original scope.

The goal of verification is a completed working result, not merely a report that something failed.
